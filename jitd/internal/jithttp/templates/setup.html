Connect Tailscale

jitd needs an API credential to set posture attributes on devices (that is how an approval turns access on) and to read the policy file (to resolve group: principals, check each flow against the policy and mark the policy snippet).

Approvals use custom posture attributes with an expiry, set through the Tailscale API; see Posture attributes API with expiry; it needs a Premium or Enterprise plan.

  1. Create an OAuth client. In the Tailscale admin console go to Settings → Trust credentials → New credential and pick OAuth. Give it a description such as jitd and, on the Scopes step, these scopes: Devices → Posture attributes: Write, Devices → Core: Read (to list someone's devices when they request from Slack) and Policy file: Read. Copy the client ID and the secret; the secret is shown once.
  2. Paste it here. {{template "tsform" .}}
{{end}}
Use an API access token instead

It works, but it expires after at most 90 days, and it can do whatever the person who made it can. An OAuth client does not expire and has only the scopes above. Create one under Settings → Keys → Generate access token.

The secret is kept in jitd's database and is never shown again, here or in the API. To keep it out of the database, put TS_OAUTH_CLIENT_ID and TS_OAUTH_CLIENT_SECRET in {{.Credentials.File}} on the host or in jitd's environment (a Kubernetes Secret, say) instead. A credential set there wins over the one saved here.

Set up outside this page

jitd needs an API credential to set posture attributes on devices (that is how an approval turns access on) and to read the policy file (to resolve group: principals, check each flow against the policy and mark the policy snippet). It reads the credential from a file on the host it runs on, so none of the admins here ever sees it.

Approvals use custom posture attributes with an expiry, set through the Tailscale API; see Posture attributes API with expiry; it needs a Premium or Enterprise plan.

  1. In the Tailscale admin console go to Settings → Trust credentials → New credential and pick OAuth. Give it a description such as jitd and, on the Scopes step, these scopes: Devices → Posture attributes: Write, Devices → Core: Read (to list someone's devices when they request from Slack) and Policy file: Read. Copy the client ID and the secret; the secret is shown once.
  2. On the host running jitd, put them in {{.Credentials.File}}, one per line, readable only by the user jitd runs as (chmod 600): 
    TS_OAUTH_CLIENT_ID=...
TS_OAUTH_CLIENT_SECRET=tskey-client-...
    An API access token (TS_API_KEY=tskey-api-...) works too, but it expires after at most 90 days; an OAuth client does not. Where jitd's platform issues it an OIDC identity token (a Kubernetes service account token, say), a federated identity with the same scopes needs no secret: set TS_OAUTH_CLIENT_ID to its client ID and TS_ID_TOKEN to the token, or to file:<path> to read it from a file (re-read as it rotates).
  3. Come back here and click Check again. No restart is needed; jitd re-reads the file and starts using the new credential if the checks pass.

Variables set in jitd's environment are used for anything the file does not set (for example when it runs in a container). Another file can be chosen with jitd -env-file.

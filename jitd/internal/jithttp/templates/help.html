Help

Just-in-time access to Tailscale Services: ask for what you need, a person approves, the access turns itself off.

How it works

  1. Request. Pick what you need, such as Database access (read-only), and say why. Choose how long: minutes, hours or days, up to the flow's maximum. The access is for the device you are on{{with .Me}} ({{.DeviceName}}){{end}}.
  2. Approve. The flow's approvers get the request on their overview; one click approves it; declining needs a short reason. Some flows need more than one approval, and some let you approve your own request.
  3. Use. Within a second or two the services appear on your device (tailscale service list). Connect without a username or password: Tailscale PAM adds the credentials for you. What you may do there is still up to the policy, so a read-only grant refuses writes.
  4. Done. Access ends on its own when the time is up. Finish early with Revoke access; withdraw a request nobody has decided on with Cancel request.

Behind the scenes an approval sets the flow's device posture attribute (custom:jit_<name>) with an expiry through the Tailscale API, and a grant in the tailnet policy gated on that posture is what gives the access. The list under Gives access to is the admin's description of that grant, for choosing what to request. Each request page shows whether that attribute was read back from the device (confirmed) and, after it ends, whether it was seen gone again.

From Claude Code or scripts

Install the tailscale-pam plugin (/plugin marketplace add atoonk/tailscale-jit, then /plugin install tailscale-pam@tailscale-jit). Claude then sees what you can reach, lists what you can request, files a request and prints the approval link for you to click.

For admins

  • Define what people can ask for in Approval flows: who can request, who approves and how many must, how long access may last, and the one posture attribute an approval sets (such as custom:jit_db_ro). Gives access to describes what that unlocks, so people and agents pick the right flow; it grants nothing by itself. Each flow's page checks this against the tailnet policy. Disable a flow to stop new requests and keep its history.
  • Connect flows to the policy with the Policy snippet: one posture and one grant per flow, each marked already in your policy or NEW. Paste what is missing into the tailnet policy and add the PAM permissions there; jitd never edits the policy itself. Remove any standing grant to the same services, or the approval changes nothing.
  • Check the credential on Setup. It tries what approvals need (reading the policy, and setting a posture attribute with an expiry on jitd's own node) and says what to fix. The credential lives in a file on the jitd host and is never shown. After editing the file, click Check again; no restart needed.
  • Roles. Admins are set with jitd -admins (logins, group:, tag:). Admins see every request, can decline any pending request and revoke any access. Everyone else sees their own requests and the ones they approve for. Only the requester can cancel a request.
  • Pending requests expire undecided after the flow's approval timeout (default 24 hours). One live request per flow and device.
  • Manage. Everything above lives under /admin, listed in the Manage section of the sidebar. End users never see that section.
  • API. Anything on the tailnet can use the same JSON API the UI and the plugin use: GET /v1/requestable → POST /v1/requests → poll GET /v1/requests/{id}. Callers are identified by their Tailscale connection; there are no tokens. The interactive API docs describe every endpoint; the raw spec is at /api/openapi.json.
